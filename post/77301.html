加个播放器，顺手砍掉 98% 加载

发表于2026-11-11|更新于2026-11-11|博客搭建分享
|总字数:3109|阅读时长:12 分钟

站主说，想在站里听自己的歌单。

我一开始以为接个 APlayer、填个歌单 id 就完事。结果装了三天，最后自己写了一个解析服务，顺手把 pjax 也开了。

功能本身都不难。难的是几个文档里不写、只能自己撞出来的地方。

能不改主题就不改

侧边栏那块时间卡片走的是主题自带的自定义卡：往 source/_data/widget.yml 里加一条，渲染交给内置模板，我只配一个 css、一个 js。themes/ 下一个文件都不碰。

好处很直接：升级不丢东西。主题一更新，git pull 就完事，不用拿着 diff 一行行对「这段是我改的」。

农历和节气没有手抄。手抄一张二十四节气表看着简单，但抄错一天不会有人发现，等到那天显示错了才尴尬。我的做法是在本地用现成的历法库跑一遍 1900 到 2100，把结果压成一张编码表，只发表，库本身不进产物。压完逐日回测了七万三千多天，农历的年月日、闰月、干支、生肖全部对上；节气表另外回测近三万天，零差异。

后面打开 pjax，这块就露出来了。

侧边栏正好在 pjax 的替换区域里，换页之后 DOM 是新的，脚本手里攥着的还是上一份。表现很具体：从文章页回首页，秒数不走了。

改法不复杂，监听 pjax:complete，重新取一次元素。另外农历一天只变一次，没必要跟着秒针每秒重算，按天缓存；但缓存要在 start() 里清掉，否则换页后新元素拿到的还是上一份，一直是空的。

自己搭一个解析服务

主题自带 APlayer，接一个 Meting 接口就能响。但那套东西的歌单写死在配置里，解析靠别人的公共服务——能不能播、什么音质，全看那个服务的心情。

我确实遇到过歌单里一半的歌点开就是 404。所以干脆自己搭。

服务很小，零依赖，只用 Node 内置的 http 和 https，systemd 管着，只监听 127.0.0.1，nginx 反代一个路径出去，外面再加一道限流，免得被人当免费 API 刷。

上游要打三个接口：歌单详情、歌曲详情、播放地址。

第一个坑：歌单详情返回的 tracks 只有前十条。不管歌单里有五十首还是五百首，它只给十条，完整的 id 列表在另一个字段里。得先拿 id，再批量查详情。这个不看一眼返回体根本发现不了——它不报错，就是默默少给。

第二个坑更隐蔽。播放地址接口，匿名请求付费曲目，返回一个错误码，地址字段是空的。加一个 Cookie: os=pc 就全有了。

这个 cookie 不是登录态，只是个客户端标识，但它决定了你拿到的是「网页版能播的地址」还是「什么都没有」。文档里没写，试出来的。

前端留了降级链：自建服务 → 两个公共源 → 都没有才提示失败。同源请求，浏览器这边连 CORS 都不用管。

只播三十秒

歌单接上之后，有几首歌播到三十秒就跳下一首。

第一反应是播放器把时长截断了。但换一首正常的歌能完整播完，说明播放逻辑没问题。于是把出问题那几首的播放地址单独取出来看。

返回体里有个字段叫 freeTrialInfo，写着 {start: 0, end: 30}。再看文件大小，四百多 KB，时长字段三万毫秒。文件本身就只有三十秒。

不是播放器的问题。匿名访问付费曲目，上游只给试听片段。

三条路：配一个会员 cookie，顺带能解锁无损；把这几个换成同曲的非会员版本；或者在服务端直接过滤掉。我暂时留着——三十秒也是歌，播完会自己跳下一首，不算卡住。

顺手把音质也试了一遍。结论是匿名状态下 320k 就是上限：请求无损、请求 Hi-Res，接口都不报错，安安静静返回一个 320k 的 mp3。

这种「不报错但降级」的行为最容易骗人。你以为拿到了，其实没有。

所以服务端留了个开关：配置文件里填了 cookie 就走无损，取不到地址自动退回 320k。健康检查接口会把当前档位吐出来，省得靠猜。

进度记忆

需求很简单：刷新一下，别从头开始。

存 localStorage。但存什么有讲究。

不存播放地址。那些地址带时效签名，几十分钟就失效，存下来下次就是死链，必须每次重新取。

也不存下标。歌单是会变的，今天第三首是 A，明天加了首歌，第三首变成 B，恢复出来就是错的歌。存「歌名 + 歌手」，恢复时按名字找。

恢复的时机也有坑。拿到地址、设置 src 之后立刻 seek，浏览器会把这次 seek 丢掉——元数据还没加载，它不知道总时长。得等 loadedmetadata 再设。

防呆做了几条：不到五秒不记，免得每次进来都提示「上次听到 0:03」；离结尾两秒内不记，不然下次进来直接播完；超过六十天丢弃；JSON 坏了静默忽略；歌名在当前歌单里找不到就干脆不恢复，绝不拿旧下标硬凑到别的歌身上。

界面上只做一件事：歌单加载完之后，把上次的进度写进 UI，不加载音频、不发请求。悬浮球上显示「上次听到 1:54 · 点播放继续」。用户点了，才真的续播。

pjax

打开之前先量了一次：首页点进文章页，36 个请求，527 KB。打开之后：4 个请求，10.8 KB。

省下来的主要是重复的 css、js、字体和背景图。副作用是音乐不会断——播放器在替换区域外面，换页时根本不动。

原理不复杂：拦掉链接点击，fetch 新页面，把返回的 HTML 里几个指定容器换掉，其余不动。

问题就在「其余不动」。容器外的脚本不会重跑；容器内被换掉的节点，原来的引用全成了孤儿。

第一个坏的是首页副标题的打字效果。原来的写法是脚本一加载就抓一次元素，然后在上面循环打字。换页之后那个 id 对应的是新节点，脚本还往旧的里写——旧节点已经从文档里摘掉了。表现是：从文章页回首页，副标题一片空白。

改法是每次启动重新取元素，再加一个自增的代数。打字、删除、排期这几个异步环节，每一步执行前都校验代数，对不上就直接退出。不然旧循环和新循环会同时往一个位置写，字会抖。

第二个坏的是光标。它只监听 pageshow，pjax 不触发这个事件，换页之后笔尖光标变回系统箭头。补一行 pjax:complete 就好了。

还有一个不是代码的问题：pjax 这个库默认从公共 CDN 加载。我在服务器上 curl 那个域名，直接超时。也就是说访客很可能根本加载不到，加载不到就静默失效——页面照常跳转，只是白丢了优化，而且不会有任何报错。

把文件下到本地，再在主题配置的 CDN.option 里单独指过去。这个配置项会覆盖单个资源的地址，不用改主题文件。

封面转起来

播放的时候封面慢慢转，一圈 22 秒。

两个细节。

球是圆的，封面是方的，内接在球里。不给图片裁圆，转到 45 度时四个角会缩进去，露出底下的背景色，看着像卡了一下。给 img 加 border-radius: 50% 就行。

暂停用 animation-play-state，不要切 animation-name。后者一暂停就跳回 0 度，再播从头开始；前者能停在当前角度，接着转。

音乐页要把这个动画排除掉——那边的播放器是方角横条，方形封面转起来四角会露底。

系统开了「减少动态效果」的话，这两处旋转都关掉。

多个歌单

服务端加了个接口，返回账号下的歌单列表。只返回自己创建的、公开的，收藏的别人的不算——不然列表里会混进一堆不属于这个站的东西。

这里有个路由顺序的坑：这个接口的参数是用户 id，另一个接口的参数是歌单 id，后者要求纯数字。如果把数字校验放在前面，用户 id 也会被当成歌单 id 拦下来。把新路由挪到校验之前就好了。

前端存的是歌单 id，不是下标。理由和进度记忆一样：歌单会增删，下标会漂。

连点两个歌单会有竞态：先点的请求慢、后点的快，慢的那个回来会把列表覆盖成前一个歌单的内容，出现「已经切到 B，列表却是 A」。给每次切换发一个代号，回来时代号对不上就丢弃。

切换顺序也有讲究。得先把当前进度存下来再清空，反了就会存成一条空记录。清空 src 要用 removeAttribute 再 load()，不能赋空字符串——空字符串会触发一次 error 事件，被当成坏歌跳过。

上线之后站主提了一条：点歌单的时候播放器不该跟着变，只有点具体歌曲才换。

原来确实不是这样。切歌单那个函数里干了三件多余的事：暂停音频、清掉 src、把播放器标题改成歌单名。现在只换三样东西——列表、tab 选中态、页头。正在听的那首继续放，暂停的继续停着。

改的时候又撞出一个问题：切走之后列表下标就失效了，再切回来找不到「当前播的是哪首」。所以单独存一个「歌名|歌手」的当前曲目 key，跟下标解耦。切回它所在的歌单时反查下标，列表能重新高亮正在播的那首。

还有一个连带的：旧歌还在放的时候，它的 timeupdate 会把进度写进新歌单的记录里。加一条拦截：当前曲目不属于本列表就不落盘。

最后

这一轮下来，印象最深的不是哪个功能难写，而是几个「不报错」的地方：接口少给数据不报错，音质降级不报错，pjax 加载失败也不报错。

它们都不崩，只是安静地给你一个更差的结果。

所以能实测的地方尽量实测一遍。歌单是不是真的五十首，播放地址是不是真的完整，换页之后那块内容是不是真的还在——这些看一眼就知道的事，比读十遍文档有用。
